\subsection*{Executive Summary}
The \texttt{memory} tool (\srcfile{src/tools/memory.ts}) is the agent's primary persistence mechanism, storing conversation history and operational state in a git-backed file (\texttt{memory/MEMORY.md}). Every \texttt{save} operation performs a \texttt{git add} followed by \texttt{git commit}, creating a permanent record of the content in the repository's history. If API keys, tokens, or other secrets are inadvertently included in memory content---either from LLM output that includes sensitive information, from user prompts containing credentials, or from tool results that leak environment variables---those secrets become permanently embedded in git history with no built-in mechanism to remove them.

The vulnerability stems from the combination of three design choices: the memory tool commits every save to git without any content inspection, the LLM may naturally include sensitive data in memory, and there is no git-secrets scanner or pre-commit hook to detect secrets before they are committed. The fix introduces a dedicated secret scanner module (\srcfile{src/secret-scanner.ts}) that uses the \textbf{gitleaks} binary (v8.18.2, 170+ rules) as its primary detection engine, with a Shannon entropy fallback (>4.5) when gitleaks is unavailable. The scanner inspects all memory content before saving and blocks the commit when secrets are detected. It also prevents secrets from being archived into the \texttt{memory/archive/} directory.

\subsection*{Root Cause Analysis}
The memory tool's save path writes content to disk and then immediately commits to git without any content inspection:

\begin{lstlisting}[language=TypeScript]
// memory.ts:153-160
await mkdir(dirname(memoryFile), { recursive: true });
await writeFile(memoryFile, finalContent, "utf-8");

try {
    execSync(`git add "${memoryPath}" && git commit -m "..."`, {
        cwd, stdio: "pipe",
    });
} catch (err: any) {
\end{lstlisting}

There is no gitleaks-integrated scanning, no Shannon entropy detection, no pre-commit hook integration, and no user confirmation prompt before committing sensitive-looking content. Once a secret reaches git history, standard git operations do not remove it---it remains visible via \texttt{git log -p} indefinitely. Removing secrets from git history requires destructive operations like \texttt{git filter-branch} or BFG Repo-Cleaner.

The \texttt{archiveOverflow} function also git-adds archive files:

\begin{lstlisting}[language=TypeScript]
// memory.ts:89-94
try {
    execSync(`git add "${archiveFile}"`, { cwd, stdio: "pipe" });
} catch {
    // Not in git, that's fine
}
\end{lstlisting}

This means archived content---which is older memory that was truncated---is also committed to git history, creating additional permanent records of potentially sensitive data.

\subsection*{Fix Implementation}
The fix introduces a dedicated \srcfile{src/secret-scanner.ts} module (303 lines) that wraps the \textbf{gitleaks} binary as its primary detection engine. Gitleaks v8.18.2 ships with 170+ built-in regex rules covering API keys, tokens, private keys, and credential patterns across dozens of providers (AWS, Azure, GCP, GitHub, Stripe, Slack, Discord, etc.). The scanner replaces a naive ad-hoc regex approach with a battle-tested, community-maintained detection engine.

The scanner's architecture is structured as follows. On first invocation, it resolves the gitleaks configuration using a priority chain: the \texttt{GITLEAKS\_CONFIG} environment variable, followed by a \texttt{.gitleaks.toml} file in the project root (which extends the default ruleset via \texttt{[extend] useDefault = true}), and finally an inline default configuration if neither is present. If the gitleaks binary is not found on the system \texttt{PATH}, the scanner automatically downloads the correct binary for the platform (Linux x86\_64, macOS x86\_64/arm64) from the official GitHub releases page. The binary is cached in a persistent temp directory at \texttt{\$TMPDIR/ga-scan-\$PID/} to avoid re-downloading across scans within the same process lifetime.

\begin{lstlisting}[language=TypeScript]
// secret-scanner.ts — core scan entry point
export async function scanSecrets(
    content: string,
    allowSecrets?: boolean,
): Promise<ScanResult> {
    if (allowSecrets) {
        return { approved: true };
    }

    const gitleaksPath = await resolveBinary();
    const result = await runGitleaks(gitleaksPath, content);

    if (result.found) {
        return {
            approved: false,
            matches: result.matches.map(maskMatch),
        };
    }

    // Fallback: Shannon entropy scan (>4.5)
    const entropyHits = shannonScan(content);
    if (entropyHits.length > 0) {
        return {
            approved: false,
            matches: entropyHits.map(maskMatch),
        };
    }

    return { approved: true };
}
\end{lstlisting}

When gitleaks is unavailable (e.g., download fails, unsupported architecture), the scanner falls back to a \textbf{Shannon entropy} scan. Strings with entropy greater than 4.5 are flagged as potential secrets, a threshold validated empirically to balance recall and false-positive rate. This fallback ensures the security guardrail is never silently disabled.

All detected secrets are masked via the \texttt{maskMatch} helper, which preserves only the first 4 and last 4 characters and replaces the middle with \texttt{****}:

\begin{lstlisting}[language=TypeScript]
function maskMatch(raw: string): string {
    if (raw.length <= 8) return "****";
    return raw.slice(0, 4) + "****" + raw.slice(-4);
}
\end{lstlisting}

Three integration points wire the scanner into the memory pipeline:

\begin{enumerate}
    \item \textbf{\srcfile{src/tools/memory.ts}} --- The \texttt{execute()} method imports \texttt{scanSecrets} and calls it before the git commit. The \texttt{allowSecrets} parameter from the tool schema is passed through to bypass scanning when the user explicitly opts in:
    \begin{lstlisting}[language=TypeScript]
const scanResult = await scanSecrets(finalContent, allowSecrets);
if (!scanResult.approved) {
    return {
        content: [{
            type: "text",
            text: `Memory contains potential secrets: ${scanResult.matches.join(", ")}. ` +
                  `Memory was NOT saved. Use allowSecrets to bypass.`,
        }],
    };
}
    \end{lstlisting}

    \item \textbf{\srcfile{src/tools/sandbox-memory.ts}} --- The sandbox variant received the same \texttt{scanSecrets} integration and \texttt{allowSecrets} passthrough, which was completely missing before the fix.

    \item \textbf{\srcfile{src/tools/shared.ts}} --- The \texttt{memorySchema} was extended with \texttt{allowSecrets: Type.Optional(Type.Boolean())} to expose the bypass flag to the LLM.
\end{enumerate}

\subsection*{Verification}
The fix is verified by 14 unit tests in \srcfile{test/secret-scanner.test.ts} that cover the full scanner surface: gitleaks detection (mock binary returns found/not-found), Shannon entropy fallback triggers on high-entropy strings, \texttt{maskMatch} correctly masks secrets, \texttt{allowSecrets} bypass flag skips all scanning, entropy is skipped when gitleaks is available, missing binary triggers auto-download, and config resolution prioritizes \texttt{GITLEAKS\_CONFIG} env over \texttt{.gitleaks.toml} over inline defaults. All 14 tests pass.
